# 两个人、不同 agent 的协作流程

## 当前状态
项目尚处于协作准备阶段。Ray 在 `Ray` 分支整理流程和可选验证技能，产品功能待双方确认。

## 两层协作
个人层：你可以使用 Pstack 的深入调查、开发和验证方法；队友可以用其他方法。
共享层：GitHub Issue、仓库文档、接口约定、PR、证据是交接依据。agent 消息可辅助沟通，最终决定必须落在这些共享产物中。

## 一个任务如何交接
1. 共同确认用户目标、成功条件和不做的内容，分配唯一负责人。
2. 有接口依赖先在 `docs/contracts/` 写具体约定，再让受影响的人确认。未选技术栈前不创建空的接口实现。
3. 各自在自己的分支开发。交接写明基准 commit、工作分支、改动范围和依赖 PR；本地路径不能当作对方可访问的资源。
4. 按 Feature Map 执行受影响的用户流程，记录动作、可观察结果和副作用。缺少前置数据时标记 blocked，不修改验收条件来获得通过。
5. PR 附复现命令、环境、结果、证据和未验证项。另一人审查接口与验收；具备应用后再添加实际适用的 CI。
6. 合并由人决定。依赖 PR 合并后，下游更新基准并重新联调；旧证据不能证明新提交。

## 证据交接
本地证据存 `artifacts/verification/<run-id>/`。分享前脱敏并检查截图、日志和钱包信息。
小型脱敏文本可随 PR 提交；大文件使用团队可访问的 PR 附件或 CI artifact，记录链接、保留期、对应 commit。
文件路径存在不等于队友可访问。私钥、token、助记词不得进入仓库或证据。

## 哪些内容进入 main
`main` 是双方共同使用的基线。项目起步时可以只保留 LICENSE。双方审阅后，以下内容适合按需通过 PR 进入：
- 介绍项目目标和启动方式的 README、共同接受的协作约定与 PR 模板。
- 已确认的接口和 Feature Map、队友可复现的验证步骤。
- 已审查的产品代码、对应测试、依赖清单和 CI 配置。

个人工具配置、试验和未定方案先留在各自分支。Ray 的 Pstack 适配技能可以继续留在 `Ray`。如果只想共享流程，就从最新 `main` 切一个小分支，只带入双方选定的文档，检查其中的链接，再提交 PR。这样每次都能单独决定哪些内容进入共同基线。

## 下一步需要共同决定
用户是谁、首批 3–5 个用户目标、验收标准、职责边界、运行环境。需求确认后再选择技术栈、写接口并开发首个纵向功能。
